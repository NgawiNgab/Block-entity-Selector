# Retargeting for a new Minecraft build

The mod never trusts a hardcoded address. Everything it needs is described in
`resources/signatures.json`, and every entry accepts a **list of candidates** that are tried in
order. That means a new game build usually needs data changes only.

---

## 1. Understand what has to be found

| JSON key | Used for | If missing |
|---|---|---|
| `render_level` | world render hook | **no highlight at all** |
| `tessellator_begin/color/vertex` | drawing | no highlight |
| `render_mesh_immediately` | submitting geometry | no highlight |
| `render_material_group` | `selection_box` material | no highlight (material required) |
| `client_instance_update` | per-tick local player | scanning never starts |
| `client_instance_get_local_player` | player pointer | falls back to vtable slot 31 |
| `actor_manager_list` | entity list | entity highlighting dead, blocks still work |
| `actor_is_player` | player/mob colour split | RTTI class-name heuristic |
| `block_source_get_block` | block id lookup | block highlighting dead |
| `level_get_hit_result`, `hit_result_get_entity` | reserved for crosshair picking | unused (picker uses actor boxes) |

Offsets (`level_renderer_player`, `actor_state_vector`, `actor_level`, …) are **probed** against
live objects on the first tick. A wrong value is rejected instead of being used, so a stale
offset degrades a feature rather than crashing the game.

---

## 2. Collect data with Zaphkiel

Zaphkiel runs inside the game process through LeviLauncher and needs no root.

1. Install Zaphkiel and launch Minecraft once so its RTTI scan can see `libminecraftpe.so`.
2. Copy `tools/zaphkiel/zInput.txt` to
   `/storage/emulated/0/Android/media/org.levimc.launcher/kurumi/zInput.txt`.
3. Run Zaphkiel, then collect from the same folder:
   - `zaphkiel_out.txt` — disassembly, resolved addresses, inline strings
   - `signatures.txt` / `signatures.json` — generated byte patterns

### Finding a function address in-game

Zaphkiel cannot guess which function is "renderLevel" by itself; use these recipes:

```
strfn<"renderLevel">                  # string xref to the render pass
strfn<"selection_box">                # the block-selection material lookup
struct<Level><0x1F0>                  # confirm Actor::mLevel layout
vft<LevelRenderer><0>                 # first virtual slot of the renderer
hier<LevelRenderer>                   # base classes, confirms the RTTI name
findclass<ActorManager>               # exact RTTI spelling for vtable entries
```

Paste each address you identify into `sig_targets.txt` (`fn<0xADDR>`) and let the generator emit a
wildcarded pattern — Zaphkiel automatically masks PC-relative instructions (ADRP/ADD/B/BL), which is
what makes the pattern survive a rebuild.

> **Tip:** prefer patterns that include the function prologue plus one or two distinctive
> instructions. Very long patterns break on unrelated refactors; very short ones hit multiple
> functions. The mod tries candidates in order, so you can list "tight" patterns first.

## 3. Convert the output

```sh
python3 tools/zaphkiel/apply_output.py \
    --signatures /sdcard/.../kurumi/signatures.json \
    --analysis   /sdcard/.../kurumi/zaphkiel_out.txt \
    --base       resources/signatures.json \
    --output     build/signatures.json \
    --game-version 1.27.0x
```

The converter:

- maps recognisable Zaphkiel labels onto the mod's JSON keys,
- puts freshly generated candidates **first** (they match the build you profiled),
- keeps the old candidates as fallbacks,
- reports anything it could not map, so you know what is still missing.

Run it with `--dry-run` to inspect the result.

## 4. Install the profile

Either:

- push it as an override — copy `build/signatures.json` to
  `<launcher mods>/BlockEntitySelector/config/signatures.json` — or
- bake it into the package by replacing `resources/signatures.json` before building.

Overrides win over the bundled file and are merged key-by-key, so a partial override file is valid.

## 5. Verify

Open the module menu → **Dump Diagnostics**. The report is written to
`<mod dir>/data/diagnostics.txt` and contains:

- the active profile (source, game version, candidate counts)
- every resolved signature with the winning candidate's origin
- every offset with the evidence that confirmed it
- renderer state (installed, frames drawn, last vertex count)
- the current selection and a rolling log

Checklist:

1. `client_instance_update` and `render_level` resolve → the mod can run at all.
2. `renderer installed: yes` and `renderer frames` keeps increasing.
3. Selecting a block you are standing in produces boxes.
4. `last draw vertices` is non-zero while a target exists.

## 6. When a signature cannot be resolved

Work down this list; each step tells you more than the previous one.

1. **Check the pattern actually exists**: Zaphkiel target `sig<AA ?? BB ...>` in `zInput.txt`.
   Zero hits means the function changed — re-derive the address (step 2).
2. **Add a second candidate**: implementations often differ by a few instructions between builds;
   two short patterns from different parts of the same function cover more ground.
3. **Use a vtable candidate instead**: many classes are stable by RTTI even when their code moves.
   ```json
   "render_level": { "candidates": [ { "rtti": "13LevelRenderer", "slot": 0 } ] }
   ```
   Resolve the right slot with `vfullvf<LevelRenderer>` in Zaphkiel.
4. **Let a feature degrade**: without `block_source_get_block` the block half of the mod turns off
   but the entity half keeps working (it only needs `actor_manager_list`).

## 7. Offsets

Each offset entry may list several candidates; the mod picks the first that survives a live probe.

```json
"actor_state_vector": {
  "candidates": [
    { "offset": "0x228", "note": "1.21-1.26 layout" },
    { "offset": "0x230", "note": "candidate for a later build" }
  ]
}
```

Probes validate semantics, not just readability:

- `actor_state_vector`: the pointer must be readable and hold finite floats inside world bounds.
- `actor_aabb_component`: the pointed-to box must be non-degenerate and finite.
- `level_renderer_player`: the camera floats must be finite.

If a probe rejects every candidate, that offset silently keeps its first profile value and the
diagnostic report calls it out — check `Dump Diagnostics` first when a feature looks broken.

## 8. Known limits of the current design

- **Block scanning is bounded** by design (radius from the player). Bedrock exposes no public
  loaded-chunk iterator that is cheap enough to walk per frame, and the mod avoids the internal
  chunk-map layout because it changes shape between builds. Entities are unbounded because the game
  already gives us the full actor list.
- **The picker is not a raycast.** It selects the entity box under the crosshair, or the block near
  the player's feet. Block-under-crosshair picking needs the player's view ray plus a block raycast;
  the hooks for that are listed above (`level_get_hit_result`, `hit_result_get_entity`) and are wired
  for a future release.
- **Entity identity is by class**, not by variant. `Zombie` covers every zombie variant the game
  reports under that class; subclasses appear as separate entries in the picker.
