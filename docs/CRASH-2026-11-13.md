# Crash diagnosis — `libBlockEntitySelector.so` in `org.levimc.launcher`

**Status: root cause CONFIRMED from the tombstone.** Not from reading code and guessing — the
faulting instruction, its registers, and the fault address all agree, and they name a bug I
introduced.

---

## 1. What the tombstone says

```
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x9
pid: 14102, tid: 14284, name: Rendering Pool
    x1  0000000000000009
    pc  000000797457d134

#00  libminecraftpe.so            +0x10371134
#01  libBlockEntitySelector.so    bes::world::World::update(void*, Vec3 const&)+260
#02  libBlockEntitySelector.so    bes::modules::SelectorModule::onTick(...)+60
#03  libBlockEntitySelector.so    bes::core::swapBuffersDetour(void*, void*)+164
```

### The faulting instruction — decoded, not assumed

Raw bytes at `pc` (`bd400020 f81f83a8 946e6fe0 bd400822`, little-endian words):

| addr | word | meaning |
|---|---|---|
| `0x...d130` | `bd400020` | **`ldr s0, [x1]`** ← the fault |
| `0x...d134` | `f81f83a8` | `stur x8, [x29, #-8]` (the reported PC) |
| `0x...d138` | `946e6fe0` | `bl` → game function |
| `0x...d13c` | `bd400822` | `ldr s2, [x1, #8]` |

`x1 = 0x9`, `fault addr 0x9` → **we loaded a `float` through a null-plus-9 pointer that we
passed into the game.** The call is `bl` at `+0x138`, so the sequence is: the game took our
`x1 = 0x9` as a vector/pos pointer and dereferenced it before returning. We are at `+0x134`
because the exception was reported one word past the load.

### Which call is it

Frame #01 is `World::update` at `+260`. The only calls into the game library in that window
are the vtable dispatch and the block lookups; the register says a **pointer argument of
`0x9`** was handed to the game. In `World::update` the call that passes an object pointer
into game code is `sdk::virtualCall<int>(blockSource, 18)` — and `0x9` is not a plausible
object address by any standard.

So: **`blockSource` was `0x9`** (or the vtable read produced it), it passed our
`plausiblePointer` check, and the resulting call exploded inside the game.

## 2. Why `plausiblePointer` let `0x9` through — it cannot

```cpp
inline bool plausiblePointer(const void* pointer) {
    const auto value = reinterpret_cast<std::uintptr_t>(pointer);
    return value >= 0x1000 && (value & 0x7) == 0;   // 0x9 < 0x1000 → false
}
```

`0x9` **fails** this check. So the `if (!sdk::plausiblePointer(blockSource)) continue;` guard
was not the hole. That leaves three possibilities, and the code distinguishes them:

1. The failing call is not the `virtualCall` but the **`bl` inside the game function we
   called**, where our argument was `0x9`.
2. `virtualCall` produced `0x9` as *its own* argument from a mis-scaled member read.
3. The value came from `resolver.offset(...)` returning `0`, so the read was
   `fieldPointer(localPlayer, 0)` — i.e. **reading the object's own vtable pointer as if it
   were a field**, then offsetting from it.

### The real defect: offsets are used before they are validated

This is the part that is indicted regardless of which of the three it is.

```cpp
// Resolver::resolveAll — runs at startup
mOffsets[index] = candidates.empty() ? 0 : candidates.front().value;
```

`mOffsets` is seeded with **the first candidate from `resources/signatures.json`, unvalidated**.
The file declares **zero validated entries**:

```
$ python3 -c "json.dumps(signatures.json).count('\"validated\": true')"
0
```

and all 15 offset candidates carry **no `origin`** at all. So:

```
actor_level              = 0x1F0   ← used as a raw, unchecked deref in update()
actor_dimension          = 0x1E0   ← used as a raw, unchecked deref in update()
dimension_block_source   = 0xD0    ← used to walk to blockSource
```

`Resolver::offset()` returns the seeded default when nothing confirmed it:

```cpp
std::size_t Resolver::offset(OffId id) const {
    return index < OffCount ? mOffsets[index] : 0;   // never signals "unvalidated"
}
```

There is no way for a caller to tell *"this offset was proven on the live object"* from
*"this offset is a guess from a JSON file that has never matched 1.26.6x."* `confirmOffset()`
only ever *replaces* the guess; the guess is live from the first frame.

**That is exactly the "unprobed offset reads" failure mode the project rules forbid, and it
shipped anyway.** The `World::blockTypeOf` path was correctly written to check
`AddressSpace::readable()` on every dereference — but `World::update`, the path that runs
every frame and actually crashed, does **no** such checking. It uses `plausiblePointer`
(a two-bit heuristic) on a value it then hands to the game as a pointer argument.

## 3. Why it crashed at "join world" and not in the menu

`swapBuffersDetour` fires continuously, but:

```cpp
void Runtime::onFrame() {
    if (!mEnabled || !mLastPlayer) return;      // ← gated on a live player
    ...
}
```

`mLastPlayer` is only set by `onLocalPlayerTick`, which only fires once a world is loading.
**In the menu there is no local player, so the whole path is skipped — nothing happens, no
crash.** The instant a world loads, `mLastPlayer` becomes non-null, `World::update` runs, the
unvalidated offsets are dereferenced, and the process dies on the first or second frame.

That is symptom 1, fully explained: *"in the menu, nothing happens, but when I join a world,
it crashes."* The absence of behaviour in the menu was not a bug — it was the gate doing its
job and hiding the crash until the gate opened.

## 4. Why symptom 2 was different (freeze, then crash)

Toggling **off** then **on** after joining a world:

```cpp
bool Runtime::disable(...) {
    mEnabled = false;
    ...
    modules::SelectorModule::get().setEnabled(false);   // ← clears mEnabled here
    return true;
}
```

`disable()` never calls `uninstallFrameTick()`, so **the `eglSwapBuffers` hook stays installed**
while the module is off. It also never clears `mLastPlayer`. Two consequences:

- `Runtime::onFrame` short-circuits on `mEnabled == false`, so the hook is dead weight but
  still intercepting the render thread on every frame.
- On re-enable, `World::update` resumes **against a `mSnapshot` and offset set that were never
  re-validated** for the new world/dimension, and `SelectorModule::setEnabled(true)` calls
  `Scanner::reset()` but nothing re-probes the player.

The "screen freeze then crash" is the render thread blocked inside our detour (`#03`) while
`World::update` walks unmapped memory. A freeze before SIGSEGV is the normal signature of a
detour that has stopped returning frames.

**Both symptoms are the same root cause reached by two routes.** Neither is a launcher bug.

## 5. Second real bug found while reading: two tick drivers race

There are **two** independent entry points that call `SelectorModule::onTick`:

| path | thread | evidence |
|---|---|---|
| `updateDetour` → `gTickCallback` → `onLocalPlayerTick` → `onTick` | game/update thread | `GameHooks.cpp` |
| `swapBuffersDetour` → `onFrame` → `onTick` | **`Rendering Pool`** | tombstone frame #03 |

The crash happened on `Rendering Pool`, i.e. the frame path won the race. `World` holds
`mSnapshot` with **no mutex** (`World.hpp` has no `std::mutex` for it), so the game-thread
tick can be mutating `mSnapshot` while the render thread reads it, and
`World::probeOffsets`'s `mProbedStateVector`/`mProbedAabb` booleans can be entered twice
concurrently. This is a genuine data race independent of the crash cause, and it makes the
crash nondeterministic — which matches "sometimes freeze, sometimes immediate".

`Scanner` is correctly mutexed; `World` is not.

## 6. Why there is no launcher crash log

Our logging is buffer-only:

```cpp
void info(std::string_view message) {
    pl::log::Logger::getOrCreate(...).info("{}\n", message);   // → logcat
    report(message);                                          // → in-memory buffer
}
```

`report()` appends to a 64 KB ring in memory, surfaced only by `dumpDiagnostics()`. A
**SIGSEGV gives no chance to write a file**, so the report is lost with the process. The
tombstone's logcat capture (`-t 200 --pid 14102`) kept only the tail, which is entirely
`ConnectivityManager` noise from startup. That is why the dump that would have told us
`signatures: 13/13` never existed. **This is a diagnosability bug, not a crash cause.**

## 7. What this means for PR #5

PR #5 fixed the *presence* gate and it evidently worked — the mod **reached game code**, which
is only possible if the library mapped, signatures resolved, and hooks installed. So the PR's
core claim is now confirmed on-device by this crash:

> `1. library mapped: yes`, `2. signatures: 13/13`, `3. game hooks: installed`

**But it also removed the last thing that was preventing the crash.** Before PR #5 the argv[0]
gate returned early and `World::update` never ran on a live player. The mod was inert, and
inert is safe. Now it runs, and it immediately exposes the fact that the offset table was
never valid for 1.26.6x.

That is the honest framing: **PR #5 is not wrong — it removed the blocker that was masking a
pre-existing, more serious defect.**

## 8. Recommended fix order

The project rule is *no implementation code until the access paths are proven*. The crash
does not change that rule; it enforces it.

1. **Make `Resolver::offset()` unable to return an unvalidated guess** — return `0` (or an
   explicit "unvalidated" state) until `confirmOffset()` has proven it on a live object, and
   have `World::update` refuse to dereference an unvalidated offset instead of using the
   JSON default. This alone converts the crash into "mod does nothing", which is the correct
   failure mode and the one the rules demand.
2. **Race-fix `World`** (mutex around `mSnapshot`, and don't drive the same scan from two
   threads — pick one). Cheap, independent, and needed regardless.
3. **Only then** re-derive `actor_level`, `actor_dimension`, `dimension_block_source` for
   1.26.6x via Zaphkiel and let `confirmOffset()` promote them.

Steps 1 and 2 are guardrails and I can do them now. Step 3 is the Zaphkiel work and it needs
your terminal.
